## Categories

For this catalog, an agent development environment is a product that gives a person a persistent place to direct coding agents, inspect their work and move changes toward delivery. Multi-agent support is something to research, not a prerequisite that would exclude useful substitutes.

| Category | Inclusion rule |
| --- | --- |
| A. Agent workspaces and orchestration | The main workflow is directing and reviewing agent work across sessions, tasks or workers. Includes local, remote and managed-cloud products. |
| B. Coding environments and agents | Editors, coding agents and software-engineering services that can substitute for part or all of that workflow. Product surfaces stay explicit. |
| C. Application builders | Prompt-to-application products that compete for the outcome of building software, often with their own hosting and deployment workflow. |
| D. Components and broader work tools | Agent runtimes, remote companions, orchestration reference projects, execution infrastructure and general work agents. Useful context for the catalog, but not automatically equivalent ADE alternatives. |

Each product gets one primary category based on its observed main workflow. These assignments are analyst judgments, not vendor labels. Local or cloud, open source or closed, single-user or team, and model-provider independence are separate attributes under the [rubric](comparison-framework.md). "Watch" and "retired" are research states, not product categories.

## Decision rules and evidence

This pass uses the rules of [the first qualification pass](qualification-2026-11.md#decision-rules-and-evidence) and the [A-D definitions](#categories) above. Runnable coding-agent workspaces and coordinators are A; coding environments, directly usable coding agents and repository bots are B; prompt-to-application builders are C. SDKs, protocols, skill packs, execution infrastructure, remote companions and general assistants remain D. A general assistant does not become an ADE simply because it can run a coding agent.

Every ledger row below gives the analyst description, category, disposition, exact first-party quotation, source locator and maintenance receipt. Vendor wording is preserved with markup removed and whitespace normalized. Short source sentences or owner-written product descriptions are used rather than the discovery input's truncated excerpts. The quotes establish the bounded description, not successful hands-on use.

Sources were retrieved on **2026-11-08**. GitHub metadata, the latest default-branch commit and the latest returned published release were checked through the authenticated read-only GitHub API. Redirects it could not follow were resolved with the read-only GitHub CLI; README content was read from first-party raw files. Public website pages and their linked changelogs, release notes or announcements supplied the website findings. A website loading, a footer year and a push to another branch do not count as dated maintenance. No installers were run.

Maintenance totals across all 231 rows are **203 yes, 8 no and 20 unknown**. Yes means dated public maintenance within the six-month window. Unknown means this pass did not establish a dated release or maintenance event; the locations checked and access gaps appear in the receipt. It does not mean inactive.

The screening cutoff is **2026-05-08**. An archived repository, unavailable registered project, latest release older than six months, or no release plus no default-branch work within six months triggers the inactive flag. KingCoding also has an explicit first-party discontinuation notice. No otherwise new unavailable identity was found after redirect resolution. A stale release is enough under this rule even when commits are recent. **Nine** flagged projects have recent maintenance: Arbor, Opcode, Aider, SWE-agent, Agent OS, AgentAPI, Agor, Container Use and PocketPaw. Four of these are ADE workflows. Recheck them before treating them as abandoned.
